# Skill 编写最佳实践指南

> 基于项目中 12 个 Skill 文档（acceptance / codereview / doc-design / doc-fullreview / doc-update / event-trade-acceptance-b / modulerefine / parking-lot / require-refine / strategy-perf-audit / test-module / workflow-capture）归纳的一般性原则。

---

## 一、文档结构规范

### 1.1 元数据头

每个 Skill 文件以 YAML front matter 开头，包含以下字段：

```yaml
---
name: <skill-name>
description: <一句话描述>。提示词：<触发关键词列表>
tags: [标签1, 标签2]
aliases: [别名1, 别名2]
---
```

**约定：**
- `description` 末尾列出所有可触发该 Skill 的用户提示词，用顿号分隔，方便 Agent 匹配
- `tags` 和 `aliases` 辅助 Agent 语义匹配，非必填但推荐

### 1.2 章节骨架

Skill 文档推荐以下结构（按需增减）：

```
§1 核心流程         — 主工作流，从输入到产出
§2 内容编写规则     — 原则 / 反模式 / 分支场景
§3 输出模板          — 最终的文档/报告格式
§4 自检清单          — 完成后的自查项
§5 禁止事项          — 不该做的事（亦可作为 §2 的子节）
§6 参考案例/附录     — 历史案例或模板
```

> 本指南的章节编号仅为示例，实际 skill 按内容多寡灵活组织。禁止事项可独立一节，也可归入原则中。

## 二、内容编写原则

### 原则 1：为用户/Agent 写出可执行的步骤

每个步骤必须是**可执行的指令**，而非泛泛描述。

```markdown
# ❌ 差
分析代码并找出问题

# ✅ 好
rg -n "for.*range\|for.*iterrows" <目标目录>
for each 命中行: 确认循环体内是否有 `df['col'] = ...`
```

### 原则 2：一条 CLI 命令胜过三段描述

给出可直接粘贴运行的 bash/python 命令，附预期产出。

```markdown
# ❌ 差
检查数据文件的列名是否规范

# ✅ 好
head -1 data/*.csv | tr ',' '\n' | sort -u    # 列出所有 CSV 的首行列名
```

### 原则 3：用表格管理多分支/映射/优先级

| 类型 | 适用场景 |
|------|---------|
| 场景矩阵 | 正常/异常/边界条件 |
| 优先级表 | P0/P1/P2 分级 |
| 映射表 | 需求→设计→测试 追溯 |
| 对比表 | 现状 vs 期望 diff |

### 原则 4：决策树 > if-else 伪代码

用 ASCII 树形结构表达分支逻辑：

```
发现的问题是否阻塞验收项的真实生效？
  ├─ 否 → 记录盲点，继续验收
  └─ 是 → 依赖链有多深？
         ├─ 改一处即可 → 直接改
         ├─ 改多处 → 列影响范围让用户确认
         └─ 涉及业务判断 → 必须问人
```

### 原则 5：Checklist 做自检

每条可独立判定通过/不通过：

```markdown
- [ ] 配置缺失 → 错误退出（不静默）
- [ ] 非法配置 → ValueError（不崩溃在其他地方）
```

### 原则 6：给出模板

为每类输出提供可直接填充的模板，减少格式争议。模板中的占位符用 `{变量名}` 表示。

### 原则 7：明确禁止事项

用独立一节告诉 Agent 什么不该做，防越界。可与 §1.2 的 §5 呼应：

```
## 禁止事项
- 不替用户做业务决策
- 不修改被审查的代码
- 不使用表情符号
```

## 三、流程设计模式

### 模式 A：先查后做（3 个 Skill 使用）

所有涉及代码分析/文档编写的 Skill，都遵循"先收集信息 → 再动手"的模式：

```
信息收集（读代码/读配置/读关联文档）
  → 分析/决策（用表格输出发现）
  → 产出（写入文件）
  → 用户确认
  → 修改/执行
```

### 模式 B：增量式处理（doc-update, codereview）

只处理自上次以来的变更，不支持全量重扫：

```
读取锚点（时间戳 / commit）
  → 增量扫描（仅处理变更部分）
  → 输出增量结果
```

### 模式 C：用户确认门控（require-refine, test-module）

关键决策点前停下，让用户确认后再继续：

```
产出→ 展示摘要 → 问"是否确认？" → 用户 say yes → 继续
                           → 用户 say adjust → 修改后再次确认
```

### 模式 D：分层分级检查（codereview, strategy-perf-audit）

按严重程度分层，高优先级通过才进入下一层：

```
P0 宪法审查（阻塞级） → P1 结构规范 → P2 运行时安全 → ...
```

## 四、常见反模式

| # | 反模式 | 表现 | 正确做法 |
|---|--------|------|---------|
| 1 | 步骤不可执行 | "分析模块"、"审查代码" | 给出具体命令 + 预期产出 |
| 2 | 无输出模板 | Agent 自己决定输出格式 | 给出 Markdown 模板 |
| 3 | 缺少前置条件 | 直接进入步骤 1，跳过准备 | §0 列出前序依赖 |
| 4 | 章节粒度不均 | 有的步骤有表格+代码，有的只有一句话 | 同级用同一模板 |
| 5 | 伪代码混入 | 用 `if/for/while` 描述流程 | 改用自然语言或树形流程图 |
| 6 | 不区分边界 | Agent 越权做业务决策 | 设立"禁止事项"节 |
| 7 | 内联大量可执行脚本 | SKILL.md 中包含 50+ 行可直接执行的 bash/python 脚本 | 提取到 `backup.sh`、`restore.sh` 等独立文件，SKILL.md 中只保留调用命令 |

## 五、Skill 存储约定

| 归属 | 路径 | 示例 |
|------|------|------|
| 全局（跨项目复用） | `/home/tp/.agents/skills/<name>/SKILL.md` | acceptance, doc-design, parking-lot |
| 项目专用 | `<project>/.agents/skills/<name>/SKILL.md` | codereview, doc-update, event-trade-acceptance-b |

### 脚本外提规则

可执行脚本（bash/python）按以下规则外提：

| 脚本规模 | 处理方式 |
|:---|:---|
| < 10 行 | 可直接内联在 SKILL.md 的代码块中 |
| 10-30 行 | 可内联，但建议外提为独立脚本 |
| > 30 行 | **必须**外提为独立文件（`<action>.sh` / `<action>.py`） |

外提后 SKILL.md 中只保留调用命令：

```bash
bash .agents/skills/<name>/backup.sh   # 脚本路径相对于项目根
```

**优势**：
- SKILL.md 瘦身 50-70%，降低每次 skill 加载的 token 消耗
- 脚本作为独立文件可被直接 `bash` 执行，不依赖 Agent 解析
- 多个 skill 可复用同一脚本（用 `bash path/to/script.sh` 引用）

## 六、自检清单

Skill 编写完成后逐项检查：

- [ ] YAML 元数据头包含 `name` / `description` / 触发关键词
- [ ] 核心流程有明确的步骤编号（1. → 2. → 3. ...）
- [ ] 每步给出可执行的命令或判断规则
- [ ] 涉及分支逻辑时用树形流程图而非伪代码
- [ ] 多维度数据用表格组织
- [ ] 输出格式有模板（非必填但推荐）
- [ ] 有"禁止事项"节（非必填但推荐）
- [ ] 关键决策点有"用户确认"门控
- [ ] 引用的路径/文件名与项目实际一致
- [ ] 同级章节详略程度一致
- [ ] 可执行脚本 > 30 行 → 已外提为独立文件，SKILL.md 中只保留调用命令
- [ ] 已排查常见反模式（步骤不可执行、伪代码混入、边界越权等）
