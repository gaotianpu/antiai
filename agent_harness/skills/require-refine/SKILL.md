## 前置条件

收到需求后先判定入口场景。按以下顺序检查：

```
该需求有现成规格文档吗？
├─ 是 → 场景 C（已有规格，需扩展/变更）
└─ 否 → 该需求有现成代码实现吗？
         ├─ 是 → 场景 B（已有代码，反推规格）
         └─ 否 → 场景 A（模糊需求，从零构建规格）
```

即：有规格走 C，有代码无规格走 B，无代码无规格走 A。

---

## 需求 vs 架构 vs 设计：三层边界

撰写全程保持三层分离。需求文档不应包含伪代码/类名/SQL/脚本路径。

**需求层**（What & Why）：功能场景, 任务流（步骤序列）, 数据字段定义, 验收标准（量化）
**架构层**（Where & How connected）：模块/包结构, 技术选型+理由, 部署拓扑, 跨模块共享的配置默认值
**设计层**（How exactly）：伪代码/算法, 文件路径+类名, API 契约/DDL, 模块内的配置默认值

> 引用方向：需求 ← 架构 ← 设计（不可逆）。需求变了架构和设计必须跟随；设计文档被删不影响需求的有效性。

## 通用原则

以下原则贯穿三种场景。逐条对照，任一命中即纠正：

| # | 信号 | 动作 |
|---|------|------|
| 1 | 功能描述只有正向流程，无异常分支 | 补异常 + 边界场景矩阵 |
| 2 | 数据字段只说"返回 K 线数据"，未给字段表 | 补字段名/类型/示例/特殊值语义 |
| 3 | 规则/策略选择无理由说明 | 补"因为 Y，选 X 而非 Z" |
| 4 | 只说"配置在文件里"，未给 `[section].key` | 精确到配置节+key |
| 5 | 代码常量在需求中无对应记录 | 补值+理由，或用"假设："标注 |
| 6 | 需求中用形容词（快/正确/安全） | 改数字：耗时<X、成功率>Y% |
| 7 | 表名/文件名/参数名在文档间不一致 | grep 全项目验证 |
| 8 | 伪代码/类名/SQL 混在需求文档中 | 上移到设计文档 |
| 9 | 需求文档出现类名、变量名、路径名、选区器等代码级名字 | 清理至设计文档。判定信号：引用了代码实现中才出现的名字就是越界 |

## 交付物模板

需求细化完成后，按此结构输出规格文档（标注 `*` 为必选章节）：

```
* §1 元数据（创建时间/最近修改/修改记录）

* §2 概述
  - 系统一句话定义
  - 核心功能 bullet（3-5 条）
  - 不做什么（否定列表）
  - 关联文档（仅列上游前置文档）

* §3 功能需求（按功能拆子节）
  每子节含：
  - 场景描述
  - 任务流：触发条件 → 输入 → 步骤序列 → 输出 → 终止条件
  - 场景矩阵（正常/异常/边界，标注优先级）

* §4 数据定义
  - 核心数据结构及字段语义（每个字段代表什么含义）
  - 写入约束（幂等/去重/不可变）
  - 特殊值语义（None vs 0 vs NULL）

* §5 非功能需求
  - 安全：密钥管理、SQL 安全
  - 性能：并发限制、超时值
  - 可观测性：关键事件的监控/通知/审计承诺

  §6 运维与调度（按需）
  - 调度表 + CLI 参数总表

* §7 约束与假设
  - 硬约束 + 外部假设 + 否决方案记录 + 已知限制

  §8 附录（按需）
```

## 场景 A：模糊需求 → 规格

用户给出极简描述（如"做一个数据导出功能"），需要从零构建规格。

### A1. 信息收集

**优先从项目内部搜索**（代码、文档、配置）——找的是相关上下文（命名规范、目录约定、可复用模式），不是找功能本身（该功能尚无代码）。确认项目内无相关信息后，再检索外部最佳实践。

```
1. grep 关键词 → 现有代码中有没有相关模块/函数/配置？
2. 读架构文档 → 模块归属、层边界
3. 读（项目已有）需求文档 → 隐含约束（支持哪些数据源/格式）
4. 读配置 → 已有相关 key
5. 读测试 → 是否已有相关用例
```

**项目内无参考时，检索行业惯例**：

| 问题域 | 方向 |
|--------|------|
| 文件格式 | 同类项目用 JSON/YAML/CSV/Parquet？ |
| 目录结构 | 业界常见 `data/`/`output/`/`cache/`？ |
| 命名规则 | `{entity}_{dim}.{ext}` 还是其他？ |
| 错误处理 | 重试/跳过/标记/终止？ |
| 并发模型 | 串行/并发/生产者消费者？ |

### A2. 场景矩阵

**先列全场景，再写流程。** bug 出在分支和边界上，不在主路径。

```
| # | 场景 | 前置条件 | 预期行为 | 优先级 |
|---|------|---------|---------|--------|
| S1 | 正常 | ... | ... | P0 |
| S2 | 异常1 | ... | ... | P1 |
| S3 | 边界 | ... | ... | P2 |
```

必须覆盖：正常路径、异常分支（网络断开/资源缺失/认证失败/数据格式异常）、边界条件（首次运行/空数据/溢出/时间跳变）。

### A3. 问题列表（按紧急度分级）

针对场景矩阵中模糊或不完整之处，逐条列出并分级（注意：这是问题的紧急度，不是代码缺陷严重度）：

| 级别 | 定义 | 不回答的后果 |
|------|------|------------|
| **阻塞** | 不回答无法继续任何设计 | 所有人阻塞 |
| **影响** | 影响核心实现但可用默认值暂代 | 后期返工 |
| **优化** | 不影响功能，仅影响体验 | 无大碍 |

输出格式：
```
| # | 问题 | 分类 | 级别 | 候选方向 |
|---|------|------|------|---------|
| 1 | ... | 数据格式 | 阻塞 | A / B |
| 2 | ... | 错误处理 | 影响 | A / B / C |
```

### A4. 逐问题决策

按优先级逐问题给出推荐。决策优先级：

1. **复用优先** — 先问"项目现有代码/配置/约定能复用多少？"，再决定新结构
2. **惯例优先** — 项目无先例查行业惯例
3. **简单优先** — 两种方案同等可行选更简单的

每条决策标注来源（复用自 X / 行业惯例 / 新建）。已否决方案记录弃用理由。

### A5. 输出

将上述收集到的信息，整理为以下格式提交用户确认。最终规格文档结构见 §交付物模板。

```markdown
## 需求细化：{需求简述}

### 场景矩阵
（正常/异常/边界表）

### 待澄清问题
| # | 问题 | 级别 | 推荐 | 理由 |
|---|------|------|------|------|

### 设计决策
| # | 决策 | 来源 |
|---|------|------|
```

## 场景 B：现有代码 → 反推规格

项目已有代码实现但缺规格文档。

### B1. 全量信息收集

同 A1，但范围更大——不只搜索相关模块，而是覆盖全链路（CLI → Pipeline → Exchange → Store）。

（待补充：B1 针对代码反推场景的额外搜索项，如调用链追踪、时序分析等）

### B2. 对照映射表

逐项 diff 代码现状 vs 期望状态：

```
| # | 维度 | 代码现状 | 期望 | 状态 | 优先级 |
|---|------|---------|------|------|--------|
| 1 | 参数名 | --coin | --coins | ❌ | P1 |
| 2 | 分页   | 无 | 有 | ❌ | P0 |
```

**缺陷严重度判定**（注意：这是代码差距的严重度，不要与 A3 的问题紧急度混淆）：
- **P0** — 数据错误/安全漏洞/进程崩溃
- **P1** — 功能缺失/设计不一致
- **P2** — 性能/日志/死代码

### B3. 转型为规格

对照映射表是分析产物，不是规格。下一步：

- **删除**：已知问题清单、宪法审查、旧代码概览
- **保留**：场景定义、配置映射、接口契约
- **新增**：CLI 参数总表、退出码、完整示例

输出规格文档时参照 §交付物模板。

## 场景 C：现有规格 → 扩展

### C1. TODO 驱动

在现有规格顶部定义目标状态：

```markdown
## TODO
- 新增场景：xxx
- 参数变更：--new 替代 --old
- 移除：--deprecated
```

### C2. diff + 冲突解决

以 TODO 为基准，逐节 diff 正文：

```
| # | 章节 | 正文现状 | TODO 要求 | 动作 |
|---|------|---------|----------|------|
| 1 | 参数表 | 5 个含 --old | 4 个含 --new | 改参数表 |
| 2 | 流程图 | 旧格式 | 新格式 | 重画 |
```

逐一修改后全文复核交叉引用和编号。输出规格文档时参照 §交付物模板。

## 自检清单

需求文档完成后逐条核查：

- [ ] 所有"支持"列表有对应的"不支持"说明？
- [ ] 每个功能有场景矩阵（正常+异常+边界）？
- [ ] 数据格式给出完整字段表（名称/类型/示例/特殊值）？
- [ ] 每条规则有理由？已否决方案已记录？
- [ ] 关键失败路径有通知承诺？关键操作有审计追溯承诺？
- [ ] 表名/文件名/参数名跨文档一致（grep 过）？
- [ ] 有元数据头（创建/修改时间）？
- [ ] 无伪代码/类名/SQL 混入需求层？
- [ ] 异常路径覆盖？边界值行为明确？单位标注？
- [ ] 每条需求可转化为一个测试用例？
- [ ] 无代码级名字（类名、变量名、路径名、选区器）混入需求层？
