# 工作流经验教训：误删除事件

> 日期: 2026-06-14
> 事件: 误删 `skills/cloudsync/backup.sh` 和 `restore.sh`

---

## 事件回顾

用户说「撤销覆盖操作」→ 执行了 `rm -rf skills/cloudsync/` 并提交删除 → 丢失两个独立脚本文件 → 从全局恢复时已是退化版（脚本内联进 SKILL.md）→ 最终从 git 初始提交 `1c44806` checkout 找回。

---

## 教训

### 1. 「撤销覆盖」≠「删除」

| 用户意图 | 应有的动作 |
|:---|:---|
| 撤销覆盖 | `git checkout HEAD~1 -- <文件>` 回退到覆盖前的版本 |
| 实际执行 | `rm -rf` 直接删除，丢失了文件 |

**规则：** 撤销操作应该用版本管理工具回退，不是手动删除。手动删除是销毁，不是撤销。

### 2. 跨位置同步时，来源版本可能已「变质」

| 位置 | 版本特点 |
|:---|:---|
| git 初始提交 `1c44806` | SKILL.md 48 行 + `backup.sh` + `restore.sh`（脚本外提） |
| 全局 `~/.agents/skills/cloudsync/` | 只有 SKILL.md（脚本内联，丢失独立文件） |

**规则：** git 历史才是权威来源，不要轻信当前文件系统的副本。

### 3. 执行破坏性操作前先确认

当时应先确认：
- 撤销哪个文件？
- 撤销到哪个版本？
- git reset 还是 checkout？

而不是直接 `rm -rf`。

**规则：** 涉及删除/覆盖的操作，先确认范围和方法，再动手。

### 4. 恢复数据的路径优先级

| 优先级 | 方法 | 适用场景 |
|:---:|:---|:---|
| 🥇 | `git checkout <commit> -- <path>` | 文件曾在 git 中 |
| 🥈 | `~/.cache/`、临时文件 | 最近操作有缓存 |
| 🥉 | 从其他副本复制 | 有同步位置（注意版本退化） |
| ❌ | `rm -rf` 后重写 | 最差选择，容易丢失信息 |
