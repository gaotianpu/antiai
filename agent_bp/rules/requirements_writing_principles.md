# 需求文档撰写方法论

## 1. 文档定位

本方法论面向 **AI Agent** 编写软件需求文档的场景——

- **输入**：一段自然语言需求描述、已有代码库、或现有草稿
- **输出**：一份结构完整、边界清晰、可直接交付给实现者的需求文档

**阅读路径：**
- 想了解需求文档与其他文档的关系 → 跳 §2「三层文档职责边界」
- 想知道怎么写才不出错 → 读 §3 每条的「反例」与「执行要点」
- 需要章节骨架 → 跳 §4「文档章节模板」
- 从零开始写 → 按 §5「撰写流程」逐阶段推进
- 写完了自查 → §6「检查清单」逐项打勾

---

## 2. 三层文档职责边界

需求文档不是孤立存在的。在开始写之前，必须先理解它在文档体系中的位置。

### 2.1 三层定义

```
需求文档 (Requirements)
  回答: 要做什么？为什么？在什么约束下做？
        What & Why & Under what constraints

  架构文档 (Architecture)
    回答: 系统由哪些部分组成？怎么协作？技术选型理由？
          Where & How connected & Why this tech

    设计文档 (Design / Spec)
      回答: 这个功能具体怎么做？给实现者什么指导？
            How exactly (implementation-level)
```

**引用方向：需求 ← 架构 ← 设计（不可逆）**——设计文档被删了不影响需求的有效性，但需求变了架构和设计必须跟随。

### 2.2 三层职责边界表

| 维度 | 需求 | 架构 | 设计 |
|------|------|------|------|
| 核心问题 | What / Why | Where / How connected | How exactly |
| 典型读者 | 产品/运维/下游调用方/新成员 | 技术负责人/高级工程师 | 实现者/Code Reviewer |
| 功能场景 | ✓ 完整描述 | ✗ 不写 | ✗ 不重述需求 |
| 任务流（步骤序列） | ✓ 属于 What | ✗ | ✓ 展开为伪代码级别 |
| 场景矩阵 | ✓ | ✗ | ✓ 展开到代码分支 |
| 数据格式（字段级） | ✓ 外部+内部 | ✗ | ✓ API 契约/DDL |
| 模块/包结构 | ✗ | ✓ 分层图+职责边界 | ✓ 文件路径+类名 |
| 技术选型 | ✗ | ✓ 选型+理由 | ✓ 具体库/版本 |
| 部署拓扑 | ✗ | ✓ 进程/容器/网络 | ✗ |
| 伪代码/算法 | ✗ | ✗ | ✓ |
| 配置参数值 | ✗ 只写参数名 | ✓ 跨模块共享的配置 | ✓ 具体默认值 |
| 验收标准 | ✓ 量化 | ✗ | ✗ |

### 2.3 越界识别

以下信号表明你正在需求文档中写本应属于架构或设计文档的内容：

| 信号 | 归属 |
|------|------|
| 出现了模块名、类名、文件路径 | 设计文档 |
| 出现了伪代码、SQL 语句、脚本路径 | 设计文档 |
| 开始讨论"为什么选 MySQL 不选 PostgreSQL" | 架构文档 |
| 画了进程/容器/网络拓扑图 | 架构文档 |

_需求文档里出现以上内容 → 上移到对应层级的文档，或标注"详见 XX 设计文档"。_

### 2.4 关联文档方向约定

- **需求文档**：只列上游（前置）——阅读本文档前必须先读哪些文档。不列下游（后继），因为下游文档可能尚不存在或路径会变。
- **设计文档**：列出上游需求 + 同级设计 + 被实现引用的代码文件。
- 正文中的导航提示（"参见 XX 文档"）用内联链接，不列入头部的关联文档块——前者是可选的阅读提示，后者容易被误解为结构依赖。

## 3. 撰写原则（12 条）

### P1：范围先闭合

**需求文档的首要职责是划定"做什么"和"不做什么"的边界。边界模糊会导致实现时凭猜测补全，发现时已是代码层面。**

| 反例 | 后果 |
|------|------|
| 列出支持的币种/周期/交易所，未说明只覆盖哪些 | 实现者在代码中硬编码差异，需求文档无记录 |
| 功能描述说"支持导出"，未说明仅部分数据源 + 仅部分周期 | 导出入口硬编码了受限的币种列表和周期，与需求预期不一致 |
| 存储方式（如交叉交易对用 spot 表存储）未声明 | 表结构设计与实际用法脱节 |

**执行要点：**
- 同一维度的所有子项必须穷举。例如"支持的时间周期"列表，缺一个就是坑。
- 如果存在差异化策略（如主流币 vs 其余币），必须在需求文档中显式列出差异点和差异理由。
- 使用「仅 / 不包含 / 以下除外」等否定句式明确排除项，比「包含 A、B、C」更安全。

---

### P2：场景矩阵先于流程描述

**流程描述（"先做 X，再做 Y"）只在主路径有效。真正的 bug 和返工出在分支路径和边界条件上。**

| 反例 | 后果 |
|------|------|
| 补缺逻辑只写了一次调用，未考虑缺口巨大时的分页循环 | 长断线时补缺不完整 |
| 重连后未触发补缺——设计了 `needs_gap_fill` 概念但初版只在启动时调用一次 | 断线恢复后数据丢失 |
| 长时间断线的降级阈值已定义但未使用——需求场景未明确 | 实现者不知道何时应触发降级 |

**场景矩阵推荐格式：**

| # | 场景 | 输入条件 | 预期行为 | 备注 |
|---|------|---------|---------|------|
| S1 | 正常消费 | 数据源正常推送 | 写入存储 + 触发下游 | 主路径 |
| S2 | 断线短时重连 | 断线 < N 分钟 | 分页补缺 → 恢复消费 | 自动恢复 |
| S3 | 断线长时 | 断线 > N 分钟 | 跳过补缺 + 告警 → 提示人工介入 | 降级路径 |
| S4 | 首次启动 | 存储无数据 | 拉最新一批数据 | 冷启动 |
| S5 | 资源不可用 | 某数据源无对应品种 | 记录到不可恢复清单 | 不可恢复 |

**执行要点：**
- 先列全场景，再写伪代码。场景改了，代码跟着改；而不是代码写了一半发现新场景，再回头改需求。

---

### P3：数据格式是一等公民

**需求文档中模糊的数据字段描述，等于把格式约定交给实现者自行猜测。猜错一个字段，下游全部受影响。**

| 反例 | 后果 |
|------|------|
| 只说"返回 K 线数据"，不说字段数量 | 测试用 7 字段 mock，生产返回 12 字段 → DataFrame 列数不匹配 → 测试绿但生产炸 |
| 字段大小写未明确 | 调了半天发现是 case 问题 |
| `start_time=0` 与 `start_time=None` 语义未区分 | `None` 表示"自动续接"，`0` 表示"从 epoch 开始"——搞反则数据全错 |

**执行要点：**
- 每个 API 返回/推送的数据结构必须给出完整字段表：名称、类型、必填性、示例值。
- 特殊值语义必须显式声明：`None` vs `0` vs 空字符串 vs 不传参数，各自代表什么行为。
- 字段 case（大小写）、类型（int / float / decimal）、精度均不可省略。

---

### P4：设计决策记录理由，不只记录结论

**"我们要做 X"没有指导价值。"因为 Y 限制，我们选择 X 而非 Z"才能避免后续有人重复论证已关上的门。**

| 反例 | 后果 |
|------|------|
| 写了规则"只在数据闭合时写入"，未写理由 | 后续无人能解释为什么不能改为写入未闭合数据 |
| 缓存刷新策略（"仅在特定周期拉取时更新"）未写理由 | 维护者不知道改动此处会影响什么 |

**决策表推荐格式：**

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A | xxx | xxx | xxx | ✓ 采用 |
| B | xxx | xxx | xxx | ✗ |
| C | xxx | xxx | xxx | ✗ |

**执行要点：**
- 每个 if/else 分支、每条规则、每种策略选择，后面跟一句「理由：...」或一个理由表。
- 已否决的方案记录为"为什么不选 Y"，防止后人提出相同提案浪费时间。

---

### P5：配置与命名是需求的一部分

**"币种列表在配置文件里"不是需求——需求必须明确：哪个配置节、哪个 key、什么格式、谁负责读写、是否有默认值和回退逻辑。**

| 反例 | 后果 |
|------|------|
| 检查工具从 `A` 配置节读列表，导出模块从 `B` 配置节读列表，两个源不一致 | 检查范围和导出范围不同 |
| 文档写脚本路径 A，实际脚本在路径 B | 阅读者按文档找代码找不到 |

**执行要点：**
- 所有可配置项必须给出「配置路径」：`[section] key`，格式（逗号分隔 / YAML / JSON），默认值，何时读取，能否热加载。
- 所有 CLI 参数必须列出：全名、类型、默认值、示例、互斥关系。
- 文件/目录路径必须与代码中的实际路径一致。

---

### P6：显式声明隐式假设

**"我们假设 API 限频是 1200/min"如果只存在于实现者的脑子里，代码 review 时就无从验证。**

| 反例 | 后果 |
|------|------|
| 硬编码币种列表，无注释说明为什么是这几个 | 增删币种时不知道应该改代码还是改配置 |
| "合约价格 ≈ 现货价格、偏差可忽略"假设未验证就写入设计 | 基于错误假设的所有计算都不可信 |

**执行要点：**
- 用「假设：...」或「前提：...」标注所有基于推测而非事实的断言。有条件时附验证方法。
- 如果一个常量出现在代码中但需求文档没提过（如并发数、超时、分页上限），补上——这就是隐式假设。
- 把没想清楚的东西用问号标记为"待确认"，不要假装它是"已确定的设计"。

---

### P7：日志、告警、可观测性是功能性需求

**"需要打日志"不是需求。"在什么时机、用什么级别、输出什么字段"才是。**

| 反例 | 后果 |
|------|------|
| 日志字段不全（如总量为 0 时无原因字段） | 无法定位根因 |
| 写入操作无行数日志 | 不知道实际写了多少条 |
| 模块用 `print()` 代替 logger | 无法统一收集和检索 |
| 导出失败无通知 | crontab 静默失败无人知晓 |

**执行要点：**
- 需求文档中应有「可观测性需求」节，列出关键事件的日志格式：时机、级别、字段。
- 告警触发条件、防抖策略、通知渠道、降级路径均应写入需求。

**日志矩阵推荐格式：**

| 事件 | 时机 | 级别 | 关键字段 |
|------|------|------|---------|
| 任务开始 | 入口 | INFO | task_name, params |
| 数据写入 | 每批 | INFO | rows_written, table_name |
| 重试 | 失败后 | WARNING | attempt, max_retries, error |
| 任务失败 | 不可恢复 | ERROR | error_type, stack_trace |

---

### P8：跨文档一致性是需求作者的职责

**"这个表名在 DDL 里没有"不是 DDL 作者的问题——是需求作者没有去查。**

| 反例 | 后果 |
|------|------|
| 表名在需求文档存在，在 DDL 和代码中不存在 | 实现者不知道建哪张表 |
| 架构文档定义了统一连接管理，但设计文档中各自独立管理 | 代码和架构脱节 |
| CLI 参数在设计文档中提到，但入口代码未定义 | 功能挂空 |

**执行要点：**
- 改需求文档中的一个表名/参数名/文件名后，立即 grep 全项目确认无残留旧名。
- 关联文档的方向约定见 §2.4。

---

### P9：需求文档本身需要版本控制

**"这个需求什么时候加的、谁加的、为什么加的"如果不可追溯，后续讨论会陷入死循环。**

| 反例 | 后果 |
|------|------|
| 需求文档无元数据头 | 不知道文档多久没更新、上次改了什么 |

**执行要点：**
- 每个需求/规格/设计文档头部应有元数据块（格式见本文档头部）：
  - 创建时间
  - 最近修改时间
  - 修改记录（每次一条：日期 + 一句描述）
- 需求变更时，在变更段落旁加注释或修改记录中标注变更原因。

---

### P10：区分「需求」「架构」「设计」

**三条线划不清楚，不同角色的读者找不到自己要的信息，拆改时也不知道哪些能动。**

> 完整职责边界表见 §2.2。此处不再重复，仅补充以下要点：

**诉求-文档索引：**

| 问题 | 去哪找 |
|------|--------|
| "这个系统是干什么的？" | 需求 §概述 |
| "支持哪些周期/币种？" | 需求 §功能范围 |
| "导出失败会通知谁？" | 需求 §可观测性 |
| "为什么选 15m 而非 1m 作为基础周期？" | 架构 §设计决策 |
| "有哪几个连接？为什么分多条？" | 架构 §连接拓扑 |
| "A 模块和 B 模块是什么关系？" | 架构 §分层图 |
| "某判断条件的逻辑是什么？" | 设计 §伪代码/算法 |
| "补缺的分页终止条件是什么？" | 设计 §详细流程 |
| "某参数设了多少？为什么？" | 设计 §配置详表 |

---

### P11：异常路径和失败模式

**"正常情况下的行为"占需求文档 90% 的篇幅，但 bug 的 90% 出在那 10% 的异常路径上。**

| 反例 | 后果 |
|------|------|
| 时间戳单位混用（秒 + 毫秒直接相加） | 计算结果偏差数百小时 |
| `start_time=0` 被 `if start_time:` 跳过 | 全量回填无法触发 |
| 空数据导致输出文件无 header | 整列数据被读成表头 |

**执行要点：**
- 每个需求场景至少包含一个异常分支："如果失败怎么办？"
- 边界值：`0`、空列表、最大值、最小值、首次调用、最后一次调用——各自的行为必须在需求中明确。
- 单位混用是高发 bug 区：文档中统一标注每个时间/金额字段的单位（秒/ms、USDT/SAT），代码中不依赖隐式转换。

---

### P12：可测试性内建于需求

**如果一条需求写完后无法用自动化测试验证，那它太模糊了。好的需求天然生成测试用例。**

| 模糊描述 | 可测试的改进 |
|----------|------------|
| "支持断线重连" | "断线后 30s 内恢复连接，60s 内补齐丢失数据，补齐后无缺口" |
| "数据格式正确" | "API 返回 12 字段 JSON，内部转换为 7 字段 DataFrame（列名: ts, open, high, low, close, volume）" |
| "并发安全" | "N 个数据源并发写入不丢数据，count(distinct source) 等于预期总数" |

**执行要点：**
- 需求描述中包含量化的验收标准。用数字（时间/次数/行数）而非形容词（快/正确/安全）。
- 边界值需求直接转化为测试的边界用例。

## 4. 文档章节模板

一份完整的、可交付的需求文档，推荐以下章节结构。每章标注「必选 / 可选 / 按需」，以及对应哪条原则。

```
§1 元数据头（必选）  ← P9
§2 概述（必选）      ← P1, P2
§3 功能需求（必选）   ← P2, P11
§4 数据存储（必选）   ← P3
§5 非功能需求（必选） ← P4, P6, P7
§6 运维与调度（按需） ← P5
§7 约束与假设（必选） ← P4, P6
§8 附录（按需）      ← P8, P10
```

### §1 元数据头（必选）

```markdown
<!--
创建时间: YYYY-MM-DD
最近修改: YYYY-MM-DD
修改记录:
  YYYY-MM-DD: 一句话描述本次修改
-->
```

### §2 概述（必选）

| 项 | 必/选 | 说明 |
|----|-------|------|
| 系统名称 | 必 | 一句话定义本系统是什么 |
| 核心需求一句话总结 | 必 | 3-5 条 bullet：系统能做什么 |
| 不做什么 | 强推 | 否定句列表，比「做什么」更能防止歧义（P1） |
| 关键任务流概览 | 必 | 列出本系统涉及的所有命令/任务入口，每条一句描述（P2） |
| 关联文档 | 必 | 仅列上游（前置）：阅读本文档前必须先读哪些文档。不列下游（§2.4） |

### §3 功能需求（必选，按功能拆子节）

每个功能子节的推荐结构：

```markdown
### §X.Y 功能名称

**场景：** 一句话描述使用场景（什么时候、谁、要做什么）。

**任务流：**
1. 触发条件 — CLI 命令 / crontab / 事件驱动
2. 输入 — 从哪里读数据（DB 表 / API / 文件 / 配置节）
3. 步骤序列 — 每步做什么，顺序/并行关系
4. 中间产物 — 过程数据放哪里（暂存目录 / 临时表）
5. 输出 — 最终写到哪里（DB / CSV / 通知）
6. 终止条件 — 什么叫"完成"

**场景矩阵：**

| # | 场景 | 条件 | 预期行为 | 优先级 |
|---|------|------|---------|--------|
| S1 | 正常 | xxx | xxx | P0 |
| S2 | 异常1 | xxx | xxx | P1 |
| S3 | 异常2 | xxx | xxx | P2 |

**数据格式：** 如果本功能涉及新的 API 请求/响应或文件格式，在此给出字段表。

**异常处理：** 失败时重试策略（次数、退避）、不可恢复时的降级行为、告警触发条件。
```

### §4 数据存储（必选）

| 项 | 必/选 | 说明 |
|----|-------|------|
| 数据库类型 | 必 | MySQL / SQLite / 选型理由 |
| 分表策略 | 必 | 按什么维度分表 |
| 表结构 DDL | 必 | 字段名、类型、精度、主键、默认值、单位（P3） |
| 写入策略 | 必 | upsert / insert-only / append；幂等性保证 |
| 连接管理 | 按需 | 连接池大小、超时、锁策略 |
| 特殊值语义 | 强推 | `None` vs `0` vs `NULL` 各自代表什么（P3） |

### §5 非功能需求（必选）

#### §5.1 代码质量

| 项 | 说明 |
|----|------|
| 架构约束 | 引用 AGENTS.md / 架构宪法（如"禁止上帝类""依赖注入"） |
| 异步约束 | 所有 I/O 设 timeout、`gather(return_exceptions=True)`、禁止阻塞事件循环 |
| 文件/函数规模 | 如项目有规模上限约束，在此明确 |

#### §5.2 安全

| 项 | 说明 |
|----|------|
| 密钥管理 | 环境变量注入，禁止硬编码 |
| SQL 安全 | 参数化查询，禁止字符串拼接 |
| 敏感文件 | 标注哪些文件不能提交到 git |

#### §5.3 性能

| 项 | 说明 |
|----|------|
| 并发限制 | 外部 API 最大并发数、DB 连接池大小、聚合并发数 |
| 超时 | REST 超时、DB 超时、WebSocket 心跳超时 |
| 内存上限 | 进程内存预期 / 容器限制 |

#### §5.4 可观测性

| 项 | 说明 |
|----|------|
| 日志矩阵 | 关键事件：时机、级别、字段（P7） |
| 告警矩阵 | 触发条件、防抖、渠道、优先级（P7） |
| 失败通知 | 定时任务失败时谁收到通知 |

### §6 运维与调度（按需）

**适用于有常驻进程或定时任务的项目。**

| 项 | 说明 |
|----|------|
| 调度表 | 任务名称、触发频率、入口命令（P5） |
| CLI 参数表 | 每个入口的参数：类型、默认值、互斥关系、示例 |
| 文件/目录约定 | 中间产物目录、输出目录、缓存文件 |
| 部署拓扑 | 容器/进程/依赖关系简述 |

### §7 约束与假设（必选）

| 项 | 说明 |
|----|------|
| 设计约束 | 来自架构宪法/运维限制的不可违反规则（P4） |
| 外部依赖假设 | API 限频、数据格式、可用性——所有基于第三方系统行为的推测（P6） |
| 否决方案记录 | 已讨论但放弃的方案 + 放弃理由（P4） |
| 已知限制 | 本系统不解决什么（如"不保证实时性低于 100ms"） |

### §8 附录（按需）

常见附录项：

| 项 | 说明 |
|----|------|
| 数据目录结构 | 树状图 + 每项用途说明 |
| CLI 命令速查表 | 一页看完所有入口 |
| 术语表 | 统一称谓（如币种代码 / 周期格式 / 表名规范） |
| 外部 API 参考 | 端点、地址、限频文档链接 |

## 5. 撰写流程

一份需求文档从零到完整，经历 8 个阶段。每个阶段有明确的核心问题和产出物，产出物落点对应 §4 模板的相应章节。阶段顺序不严格串行——实践中经常回溯（场景不全时回退补充、数据格式定义后触发范围调整等）。

```
阶段 1        阶段 2        阶段 3              阶段 4
素材收集  →  范围界定  →  任务流+场景枚举  →  数据契约
  │              │              │                    │
  └──── 回溯 ────┴──── 回溯 ────┴────── 回溯 ──────┘
                                          │
阶段 5        阶段 6        阶段 7        阶段 8
约束与假设  →  可观测性  →  交叉验证  →  审查定稿
  │              │              │              │
  └──── 回溯 ────┴──── 回溯 ────┴──── 同步 ────┘
```

### 阶段 1：素材收集

**核心问题：** 要解决的业务问题是什么？已有的系统长什么样？

| 素材来源 | 具体动作 | 对应原则 |
|----------|---------|---------|
| 用户/下游的需求描述 | 记录原始表述（不要翻译），标注来源和日期 | — |
| 已有代码实现（如有） | 走读现有入口、数据流、配置，记录「做成了什么」而非「怎么做的」 | P10 |
| 同类系统参考 | 标注引用的外部系统行为，避免"跟 XX 一样"的模糊描述 | P6 |
| 已知约束 | 从 AGENTS.md / 架构宪法 / 运维手册中提取不可违反的硬约束 | P4 |

**产出：** 一份原始素材笔记（可以散乱，不需要结构化）。核心是确保「别人的需求」和「系统的现状」都不被遗漏或曲解。

---

### 阶段 2：范围界定 → 输出到模板 §2

**核心问题：** 文档管哪块？不管哪块？谁来读？

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| 写「概述」段 | 一句话说清本系统要达成什么（不是怎么达成） | — |
| 写「不做什么」 | 用否定句列出明确排除的需求，比「包含」列表更防歧义 | P1 |
| 写「阅读对象」 | 标注本文档的目标读者（实现者 / 运维 / 下游调用方），决定后续章节的详细程度 | P10 |
| 写「关联文档」块 | 仅列上游（前置）文档。不列下游（§2.4） | P8 |

**产出：** 一个带有「概述」「不做什么」「关联文档」的文档骨架（模板 §2）。

---

### 阶段 3：任务流 + 场景枚举 → 输出到模板 §3

**核心问题：** 这个命令/任务启动后，从开始到结束要做什么？中间有哪些情况？

这是需求文档最核心的产出。一个任务流如果不能在需求阶段画清楚，实现者必然凭猜测补全——而补齐的部分大概率出错。

#### 3a. 先画任务流（Happy Path）

任务流描述"一切正常时，从触发到完成的全过程"。必须在需求阶段确定——它不是设计细节，它就是需求本身。

任务流的推荐格式：**步骤编号 + 动作 + 输入/输出 + 依赖**，而非伪代码。

| 要素 | 说明 |
|------|------|
| 触发条件 | 谁/什么启动它？（CLI / crontab / 事件驱动） |
| 输入 | 从哪里读数据？（DB 表 / API / 文件 / 配置文件） |
| 步骤序列 | 每一步做什么，顺序是否严格，哪些步可并行 |
| 中间产物 | 过程性数据放哪里？（暂存目录 / 临时表 / 内存） |
| 输出/副作用 | 写到哪里？（DB 表 / CSV 文件 / 通知） |
| 终止条件 | 什么情况下算"完成"？（全部处理完 / 时间窗口闭合 / 遇到不可恢复错误） |

**典型反例（需求阶段未回答的问题 → 代码中出现魔法数字）：**

- 脚本启动后，先查 DB 的最新时间戳还是先读缺口文件？两者顺序影响冷启动行为。
- 逐行处理时每行结束后要不要 sleep？sleep 多久？需求没写 → 代码里到处是 `time.sleep(0.5)` 魔法数字。
- 补完后要不要重新验证零缺口？需求写了这一步才是清楚的任务流，漏了这一步实现者也会漏。

#### 3b. 再穷举分支与边界

有了主任务流作为基线，才能逐步问"如果失败怎么办？"

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| 穷举分支 | 对主任务的每一步问"如果失败怎么办？"，列出所有可恢复/不可恢复的分支 | P2, P11 |
| 穷举边界 | 首次运行、最后一次运行、空数据、溢出、时间跳变——每项一条场景 | P11 |
| 构建场景矩阵 | 将上述所有场景写入一张表（编号 + 条件 + 预期行为 + 备注），填入模板 §3 的「场景矩阵」段 | P2 |
| 定义优先级 | 标注每条场景的优先级（必须实现 vs 降级可接受 vs 可延后），供实现者排期 | — |

**产出：** 一份任务流（步骤编号 + 动作 + 输入/输出 + 终止条件）+ 一张场景矩阵表。两者填入模板 §3。

---

### 阶段 4：数据契约 → 输出到模板 §4

**核心问题：** 数据从哪来、长什么样、到哪去？

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| 外部数据格式 | 对每个外部 API / 推送 / 文件，给出完整字段表：名称、类型、示例值、可否为空 | P3 |
| 内部存储格式 | 对每张表/文件，给出字段定义、主键、索引、默认值、特殊值语义（`None` vs `0`） | P3 |
| 字段映射 | 外部格式 → 内部格式的转换规则（截断、重命名、case 转换、精度处理） | P3 |
| 单位标注 | 每个时间/金额/数量字段标注单位（秒/ms、USDT/SAT、整型/浮点） | P11 |

**产出：** 至少两张表——外部数据格式表 + 内部存储 DDL / 文件格式表。填入模板 §4。

---

### 阶段 5：约束与假设 → 输出到模板 §7

**核心问题：** 哪些是确定的？哪些是推测的？

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| 列出硬约束 | 从架构宪法/运维限制中提取不可违反的规则（必须异步、必须 timeout、必须参数化 SQL 等） | P4 |
| 列出配置项 | 每个配置项的 `[section].key`、格式、默认值、能否运行时修改 | P5 |
| 列出假设 | 用「假设：...」标注所有基于推测而非事实的断言，标验证方法 | P6 |
| 记录否决方案 | 对已讨论过但放弃的方案，记录"为什么不选"——一行足够 | P4 |

**产出：** 约束表 + 假设清单。填入模板 §7。

---

### 阶段 6：可观测性 → 输出到模板 §5.4

**核心问题：** 运行起来之后，怎么知道它是好是坏？

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| 日志矩阵 | 关键事件表：时机（XXX 完成/失败）、级别（info/warning/error）、字段（coin/tf/rows/duration） | P7 |
| 告警矩阵 | 触发条件（延迟 > N 分钟）、防抖策略（连续 N 次后发送）、渠道、优先级 | P7 |
| 失败通知 | 对 crontab/后台任务型功能，必须定义失败时的通知路径 | P7 |

**产出：** 日志矩阵 + 告警矩阵。填入模板 §5.4。

---

### 阶段 7：交叉验证

**核心问题：** 本文档说的话，和别的文档/代码是否一致？

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| grep 表名 | 本文档提及的每张表/每个文件，在 DDL / 代码 / 其他 spec 中确认存在且签名一致 | P8 |
| grep 配置 key | 本文档提及的每个 `[section].key`，在配置文件中确认存在 | P5, P8 |
| grep CLI 参数 | 本文档提及的每个 CLI 参数，在入口代码中确认已实现（或标注"待实现"） | P5, P8 |
| 走读已有代码 | 如果已有部分实现，逐条对照：已实现的做标注，未实现的标 TODO，有偏差的记录需要对齐 | P10 |

**产出：** 一份「差异清单」（已实现 / 未实现 / 有偏差）。

---

### 阶段 8：审查定稿

**核心问题：** 这份文档能不能交给别人开始写了？

| 动作 | 说明 | 对应原则 |
|------|------|---------|
| 用检查清单逐项过 | 对照 §6「检查清单」的 12 条，逐项打勾 | P1-P12 |
| 找人读一遍 | 找一位不了解此系统的同事，看能否仅凭需求文档说出要做什么（不要求说出怎么做） | P12 |
| 标注修改记录 | 元数据头补充本次创建/修改记录 | P9 |
| 补充验收标准 | 对没有量化标准的需求，补数字：耗时、成功率、数据量、延迟上限 | P12 |

**产出：** 一份可以交付给实现者的、完整的需求文档。

---

## 6. 检查清单

写完一份需求文档后，用以下 12 条逐项自查：

- [ ] **P1** 所有"支持"列表是否有对应的"不支持"说明？差异化策略是否显式列出？
- [ ] **P2** 每个关键任务是否有端到端的任务流（触发→步骤序列→中间产物→输出→终止条件）？场景矩阵是否覆盖了重连、首次启动、长时间断线、资源缺失？
- [ ] **P3** 数据格式是否给出完整字段表（名称、类型、示例值、特殊值语义）？
- [ ] **P4** 每条规则/约束是否有理由？已否决的方案是否记录？
- [ ] **P5** 配置路径是否精确到 `[section].key`？CLI 参数是否有类型/默认值/互斥关系？
- [ ] **P6** 所有硬编码常量（并发数、超时、分页上限、列表）是否在需求中有对应记录？
- [ ] **P7** 日志/告警是否有时机、级别、字段矩阵？导出/补缺等关键路径失败是否有通知？
- [ ] **P8** 本文档引用的表名/文件名/参数名是否与其他文档一致？是否 grep 过？
- [ ] **P9** 是否有元数据头（创建时间、最近修改、修改记录）？需求变更是否标注原因？
- [ ] **P10** 是否有模块名/类名/伪代码/SQL/脚本路径混入需求层？这些是否应上移到架构或设计文档？
- [ ] **P11** 异常路径是否覆盖？边界值（0 / 空 / 极大值）行为是否明确？单位是否统一标注？
- [ ] **P12** 每条需求是否能转化为一个测试用例？验收标准是否量化？
