## 核心流程

### 1. 信息收集 + 对照映射                     ◀── 阶段1 理解现状

- 读取 `docs/architecture_overview.md` → 确认模块归属层、期望定位、已知问题
- 读取模块源码 → 记录行级关键逻辑
- 读取 `config/main.ini` → 反推配置驱动的期望能力
- 读取相关设计文档（`docs/specs/`、`docs/rules/`）→ 提取 API 设计、约束条件
- 检查 `docs/analysis/tests-index.md` → 确认模块是否已有测试规格和测试代码（同步更新提示方法见步骤6）

**对照映射**（模块已有文档+代码时执行）：
- 读取所有相关设计文档 → 逐项 diff 文档与代码，产出对照表，标注 ✅/⚠️/❌
  - ✅ = 文档与代码一致
  - ⚠️ = 存在差异，需讨论（参数/功能是否有必要保留、是否为历史遗留）
  - ❌ = 文档描述的功能未实现，或代码逻辑与文档矛盾
- **⚠️ 项立即质疑**：参数/功能是否为历史遗留，是否可以移除——不要拖到代码重构阶段才处理
- diff 表作为分析文档的素材收入（方法见步骤3）

### 2. 设计确认（条件步骤）                     ◀── 阶段1 确认方向

> 触发条件：步骤1中发现 ⚠️ 项，或模块状态为"零代码/空壳"/"设计讨论中"。

- 列出所有待定功能、参数、输出格式
- 逐项确认：**核心功能**（必须有）/ **可选功能**（可加可不加）/ **不需要**（移除）
- 确认输出格式、文件命名规则、默认行为
- **教训**：新增参数/功能前先问一句"这是核心还是可选"，避免写了再删
- **交互方式**：向用户列出待定项清单，逐项标注建议分级（如"建议移除 `--dir`，为历史遗留参数"），等用户逐项确认后再进入步骤3

### 3. 结构化产出                              ◀── 阶段1 固化分析

**铁律：完成分析后立即保存为文档**。后续所有深入讨论围绕该文档展开，采用追加方式而非新建文件。

**落笔前先列章节骨架**（草稿标题列表），确认章节顺序符合认知流（宏观定位 → 内部机制 → 问题方向），再逐章展开——避免落笔后反复调整结构。

选择一种输出模板：

| 模块状态 | 模板 | 文件名 | 参考 |
|---------|------|--------|------|
| 零代码/空壳 | 期望 vs 现状 差距表 + 实施路线图 | `{module}-gap-analysis.md` | workflow-notification-gap.md |
| 有代码，架构有期望 | 职责总览 + 初始化/运行时流程 + 待修复清单 | `{module}-analysis.md` | workflow-tradeos.md |
| 有代码，纯分析 | 架构图 + 数据流 + 类职责表 + 已知问题 | `{module}-analysis.md` | workflow-signals-module.md |
| 设计讨论中 | 场景表格 + 逐行深化 + 伪代码 | `{module}-design.md` | workflow-fra-scenarios.md |
| 有代码，已有分析文档需验证刷新 | 分步走查调用链 + 文档 vs 实现 diff 对照表 + 补充发现 | `{module}-flow-trace.md` | workflow-signals-flow-trace.md |

保存路径：`docs/analysis/{module}-分析文档名.md`。

**"验证刷新"模板附加步骤 — 文档 vs 实现 diff**：
1. 从已有分析文档逐条提取关键断言（架构图、数据流、数据结构、已知问题、修复状态）
2. 对照源码逐条验证，产出"无差异 / 有差异 / 补充发现"三列对照表
3. 补充发现分为：未使用工具函数、硬编码默认值、过时引用
4. 检查关联归档文档（`docs/archive/`）是否与本分析文档矛盾，如有则标注过期

**初稿自查**：
- 回答同一问题的章节是否相邻？（如层级对比表 + 架构全景图应在同一节）
- 是否有重复内容可合并？（如源码目录树 + 类职责表）
- 章节顺序是否符合"宏观定位 → 内部机制 → 问题方向"的认知流？
- 术语是否按 `docs/glossary.md` 使用了正确的指代？混用了"App/策略/信号策略"？
  发现问题 → 先在 glossary 补充定义 → 再批量替换

### 4. 宪法审查                                ◀── 阶段1 合规检查

对照 `docs/rules/unix_pythonic_guid.md` Agent 速查清单 12 条信号，逐条过：
- [ ] 无上帝类/全局状态/单例
- [ ] 依赖显式注入
- [ ] 无 except: pass / return None 代替异常
- [ ] 无 isinstance 类型分发 / 单子类 ABC / 5+ if-elif 分支
- [ ] 模块放在正确目录下（参照 `development_preferences.md` 决策树）
- [ ] 机制层不 import 应用层（参照 `architecture.md` §5 违宪检测信号）

### 5. 迭代细化                                ◀── 阶段2 用户追问

> 条件步骤：若用户未经过追问（如直接从阶段1跳到"把这些全修了"），跳过此步直接进入步骤6。

用户深度参与，从三个角度注入领域知识：结构直觉（"层级表应该和架构图在一起"）、业务背景（"信号分定时和事件两种"）、术语敏感（"策略应该用 App 代替"）。Agent 角色：接受纠偏 → 找宪法/代码背书 → 回填文档。

- **追加不新建**：后续深入讨论直接在已保存的分析文档上追加章节
- **用户纠偏优先**：用户说"这两个其实一样"时，先接受再找宪法条款背书
- **追问即素材**：用户追问的细节问题（如"缓存过期会发生什么"）的答案本身就是文档素材，应回填到分析文档
- **逐点确认**：不是"全改好再给我看"，而是"改一行，确认一行"
- **拿不准的标记待定**：不做业务决策（策略盈亏、参数阈值等）
- **进入修复**：用户确认分析结论后，在分析文档中标注"已确认可修复"，然后进入步骤6

### 6. 分析→修复闭环                            ◀── 阶段3 代码修复

分析文档中的"修正方向"经用户确认后可以落地为代码修改：

- 用户指定修复范围（如"P0 解决这2个问题"）→ 逐项执行
- 修复完成后在分析文档中标注状态（"已修复" / "设计决策"）
- 已修复项从"已知问题"移入独立"已修复问题"小节，保留修正描述
- 不被修的问题降级到"已知问题"或标注为"设计决策"
- **测试同步提醒**: 若阶段 1 检测到该模块已有测试规格/代码，执行修复前提示用户：
  ```
  ⚠️ {模块} 已有测试：
     - spec: docs/analysis/{module}-test-spec.md
     - code: tests/test_{module}.py
  设计/实现变更可能破坏已有测试，是否需要同步更新？
  ```

**实时文档同步约束**（适用模板：有代码+架构期望 / 验证刷新）：
- **实现一项功能，立即同步一次设计文档**——禁止攒到最后批量修
- 文档同步目标：模块设计文档（`docs/modules/`）或步骤3产出的分析文档，视情况而定
- 每次同步以追加方式更新对应章节，并在分析文档中标注"已同步文档"

### 7. 边界测试（条件步骤）                      ◀── 阶段3 验证

> 触发条件：步骤6执行过代码修复，且模块有运行入口。

- 全币种 + 全周期跑一次验证（如 `--symbols all`、`--timeframe all`）
- 修复 config 缺失节、边界值等问题（如 `[coin_default]` fallback）
- 若阶段1检测到已有测试代码，运行测试确保无回归

### 8. 代码审视                                ◀── 阶段3 收尾

全部修复完成后，统一审视代码质量：

- 审视耦合度（视图与逻辑是否解耦，可抽取独立函数）
- 审视函数排列顺序（按依赖层次排列：数据→工具→检查→视图→编排→入口）
- 审视冗余参数/逻辑（对照映射时未发现的遗留问题）
- 若修复阶段引入新代码，此时补跑宪法审查
- **注意**：代码审视必须在文档规整之前执行（避免"规整文档 → 代码重构 → 文档又过时"）

### 9. 文档规整 + 关联文档同步                   ◀── 阶段3 收尾

- **文档规整**：全文扫描去重重组（如果步骤6实时同步文档做得好，这一步很小）
  - 扫描 5 类问题：重复内容、过时描述、章节错位、认知流差、术语不一致
  - 参考 `doc-fullreview` skill 方法论
- 检查是否有冗余文档可删除（如分析文档已覆盖使用指南内容）
- 检查引用该模块的其他文档是否过时
- 更新 `docs/README.md` 索引
- 在关联文档间建立交叉引用
- 追加操作记录到 `docs/changelog/log.YYYY-MM-DD.md`

## 弯路教训与流程约束

> 参考 `docs/analysis/workflow_check_ohlcv_data.md`。

| 弯路 | 根因 | 本 Skill 流程约束 |
|------|------|-------------------|
| `--verbose` 加了又删 | 设计没确认是核心/可选就动手 | 步骤2 设计确认：新增参数前先分级 |
| `--dir` 历史遗留拖到重构才删 | 对照映射时未质疑必要性 | 步骤1 对照映射：⚠️ 项立即质疑 |
| Skill 格式来回调 3 轮 | 落笔前没确认章节骨架 | 步骤3 初稿自查：先定骨架再填内容 |
| 文档更新攒到第 4 轮批量修 | 未养成实时同步习惯 | 步骤6 实时文档同步约束 |
| 配置缺节运行时报错 | 未提前做全周期边界测试 | 步骤7 边界测试：修完立即全量验证 |
| 文档规整先于代码重构 | 审视与规整顺序颠倒 | 步骤8→9 顺序约束：审视在先，规整在后 |

## 禁止事项

- 不替用户做业务决策（策略参数、风控阈值、交易逻辑）
- 归属层未确认，禁止移文件
- 先讨论方案，再改代码
- 修正方向须用户确认后执行，不自作主张
- 同一模块不拆散到多个文件，优先追加到已有文档
