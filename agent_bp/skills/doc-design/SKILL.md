# 设计文档编写指南

用户指定一个模块，为之编写或审查设计文档。本文档与 `app_doc_lifecycle.md`（文档生命周期职责划分）互补，聚焦具体写法。

---

## 1. 前置阅读

动手前先搞清楚三件事：

1. **读需求文档** — 如果项目有需求规格文档，通读一遍，提取场景矩阵、数据格式、配置参数名
2. **读关联共享文档** — 了解可用的共享接口契约
3. **读已有代码** — 如果已有骨架或实现文件，查看对应模块的目录结构、类名、方法签名

> 没有需求文档？先退回需求阶段，不直接写设计。
> 已有实现跟需求不一致？标注差异，先确认需求再决定设计走向。

---

## 2. 章节骨架

设计文档推荐以下章节结构：

```
§1 概述          — 一句话定位 + 上游需求引用 + 设计决策
§2 类设计        — 主类 + 关键数据类
§3 核心流程      — 主循环 + 信号处理 + 核心算法流程说明（自然语言 + 树形流程）
§4 子模块/适配器  — 各子模块接口 + 实现
§5 配置映射      — 需求配置路径 → 设计参数
§6 文件结构      — 文件清单 + 预估行数
§7 相关文档      — 交叉引用
```

---

## 3. 逐章编写要点

### §1 概述

**元数据头（必填）：**
```markdown
<!--
创建时间: YYYY-MM-DD
最近修改: YYYY-MM-DD
修改记录:
   YYYY-MM-DD: 初版
-->
```

- **最近修改** 每次修改都要更新
- **修改记录** 每追加一行，不删除历史。描述用一句话说清变更原因和范围
- **上游需求** 精确链接到对应的 `.requirements.md`，如 `[event-trade.requirements.md](event-trade.requirements.md)`
- **设计范围** 用否定句划定边界："本文档不重复需求文档中的场景矩阵和业务规则"
- **设计决策** 每一条决策都写理由。如果有备选方案被否决，记录"为什么不选"
- **待明确事项** 用 `(待明确)` / `(待讨论)` 标注在修改记录或正文中，方便后续追踪

### §2 类设计

用 Python 风格描述关键类：

```python
class MainClass:
    """一句话职责描述"""

    def __init__(self, portfolio_name: str, config: dict, logger=None):
        # 只声明依赖和配置解析，不做 I/O
        ...

    async def execute(self) -> bool:
        """入口方法 — 描述生命周期"""
        ...

    async def cleanup(self) -> None:
        """清理资源"""
        ...
```

**关键数据类**也在此定义，用 `dataclass` 风格：

```python
@dataclass
class PositionState:
    symbol: str
    direction: str
    quantity: float
    open_price: float
    open_time: int       # Unix 秒
```

**状态管理**说明：数据存内存还是持久化？重启后是否恢复？写理由。

### §3 核心流程

#### 3.1 主循环（顶层编排）

用 `│ ├─ └─` 树形流程画出生命周期：

```
execute()
  │
  ├─ 初始化组件（init_listener）
  ├─ 启动后台协程（exit_check_loop）
  └─ 阻塞等待，直到被外部取消
```

强调两点：
- **启动即崩溃**：初始化失败必须 raise，不允许 `log.error + return`
- **优雅关闭**：`cleanup()` 停止监听 → 关闭连接 → 清理状态

#### 3.2 信号/数据处理流程

需求文档中的场景矩阵在这里展开为**流程说明**，每步标注 I/O 类型：

```
_on_signal_received(raw_data)
  │
  ├─ 1. 时间比较（无 I/O）
  │     └─ now - timestamp > max_age → stale, skip
  │
  ├─ 2. 去重检查（无 I/O）
  │     └─ 有活跃持仓 → skip
  │
  ├─ 3. 合法性检查（并行 I/O）
  │     └─ 对每个 item 查交易所 symbol_info
  │
  ├─ 4. 资金分配（无 I/O，纯函数）
  │     └─ capital_allocation_func(n) → per_item_capital
  │
  └─ 5. 执行开仓（并行 I/O + 串行 I/O）
        └─ 并行下单，全部完成后统一对账
```

**写法要点：**
- ✅ 标注哪些步是 I/O（需 await）、哪些是纯计算（同步）
- ✅ 明确并行 vs 串行，并写理由
- ✅ 用自然语言说明约束（如"所有并行 I/O 设超时"、"gather 使用 return_exceptions=True"）
- ⚠️ 保护策略/条件判断不要在第一个条件里 `return` 导致后续策略被跳过——用顺序管道，明确每个策略是"延迟退场"还是"修改参数"
- ✅ 配置结构和接口签名可以用 Python 风格的类/方法定义
- ❌ **禁止 Python 关键字伪代码**（`if/for/await/asyncio.gather` 等）— 不可执行、不可验证、会过时。算法细节用验收脚本（pytest）表达

#### 3.3 退场/定时检查循环

高频循环要标注：
- **检查间隔**：有持仓 / 无持仓是否不同？理由？
- **退出条件**：正常退出 / 异常重启 / 被取消
- **反向信号/保护策略**的触发时序

### §4 子模块/适配器

**适配器模式**的标准写法：

```python
class TriggerSource(ABC):
    @abstractmethod
    async def start(self, callback: Callable):
        ...

    @abstractmethod
    async def stop(self):
        ...
```

列出所有内置实现，每个标注：
- 文件名
- 适用场景
- 关键依赖（文件系统 / Redis / 等）

**工厂选择**用简单 dict 映射，不用 Factory 类：

```python
REGISTRY = {"file_watch": FileWatchTrigger, "redis_pubsub": RedisPubSubTrigger}
```

### §5 配置映射

需求文档中的 YAML 配置路径映射到代码参数：

| 配置路径 | 设计映射 | 类型检查 |
|---------|---------|---------|
| `trigger_mode` | → `create_trigger()` | 枚举校验 |
| `exit.trigger.take_profit` | → `self._exit_config["take_profit"]` | float > 0 |
| `exit.execution.mode` | → `self._exit_config["mode"]` | "once" / "batch" |

**类型检查**标注每个字段的验证规则（>0 / 枚举值 / 范围）

### §6 文件结构

```
<模块目录>/
├── main.py            # ~150 行 — 主类 + 流程编排
└── sub/
    ├── __init__.py
    ├── base.py         # ~15 行 — 抽象基类
    ├── impl_a.py       # ~80 行 — 实现 A
    └── impl_b.py       # ~80 行 — 实现 B
```

**规模预估**：每文件 ~行数 + 职责描述。总行数应 < 500（避免设计过度复杂）

### §7 相关文档

只列出**被引用**的文档（上游需求 + 共享规格），不列"可能需要看"的文档：

```
- [`{module}.requirements.md`]({module}.requirements.md) — 上游需求
- [`{module}.test-spec.md`]({module}.test-spec.md) — 测试规格
- `{project_specs}/shared/{接口文档}.md` — 共享接口
- `docs/rules/app_doc_lifecycle.md` — 文档生命周期职责 + 代码/伪代码原则
```

## 4. 从需求到设计的映射检查

设计文档完成后，逐条核对需求文档的场景矩阵：

| 需求场景 | 设计覆盖 | 状态 |
|---------|---------|:----:|
| S1 收到信号 | §3.2 信号处理 → 1→2→3→4→5 | ✅ |
| S2 重复信号 | §3.2 步骤 2 去重检查 | ✅ |
| S3 余额不足 | §3.2 步骤 4 资金分配（小于 min_cost 时跳过） | ✅ |

**必须覆盖所有 P0 场景。** P1/P2 如果在设计文档中明确标记"第二期实现"，需在修改记录中说明。

---

## 5. 与测试文档的联动

设计文档定稿后，检查测试规格（`.test-spec.md`）：

- 测试用例是否覆盖了设计文档中的核心流程分支？
- 设计文档中新增的纯函数（如 `capital_allocation_func`）是否在测试规格中增加了对应用例？
- 配置映射表中的新字段是否有对应的配置校验测试？

**发现缺失** → 在测试文档头部修改记录追加一条标注，或在当前会话中同步补充。

## 6. 自检清单

完成设计文档后逐项打勾：

### 结构完整性

- [ ] 有元数据头（创建时间、最近修改、修改记录）
- [ ] 上游需求链接正确（相对路径可跳转）
- [ ] 每章都有内容，没有"待补充"空小节
- [ ] 文件 ≤ 500 行（超标说明边界没划清楚）

### 流程描述

- [ ] 主循环有树形流程说明
- [ ] 信号/数据处理的每一步标注了 I/O 类型
- [ ] 并行/串行有明确说明和理由
- [ ] 关键约束用自然语言说明（如超时、return_exceptions=True）
- [ ] 无 Python 关键字伪代码（if/for/await/asyncio.gather）— 用自然语言或树形流程替代
- [ ] 保护策略/条件判断是顺序管道，不会因第一个条件截断后续

### 边界 & 约束

- [ ] 没有框架内部引用（无具体框架/App 名）
- [ ] 共享组件引用 shared/ 文档，不重复描述
- [ ] 待明确事项已用 `(待明确)` 标记
- [ ] 配置映射表有类型检查规则
- [ ] 重启后状态恢复策略有说明

### 跨文档一致性

- [ ] 所有需求 P0 场景有设计覆盖
- [ ] 纯函数有对应的测试用例
- [ ] 配置参数名与需求文档一致
- [ ] 修改记录已同步
